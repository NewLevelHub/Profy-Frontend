# PRO-242 — что нужно от бэкенда

Собрано во время UX-редизайна админки. Фронт в рамках PRO-242 **не** обходит эти
пробелы выдумыванием данных: там, где API не отдаёт нужного, UI либо честно
показывает «—», либо функция не строится вовсе. Ниже — список того, что
разблокирует уже спроектированный интерфейс.

Порядок — по влиянию на работу админа.

---

## 1. Сортировка в списковых эндпоинтах

**Сейчас.** Ни один список не принимает `sort` / `order`:
`GET /admin/users`, `/admin/universities`, `/admin/feedback`, `/admin/questions`,
`/admin/question-pairs`, `/admin/motivation-statements`, `/admin/motivation-pairs`,
`/admin/directions` — только `page` / `limit` (+ у части `search` и фильтры).

**Почему это блокер.** Клиентская сортировка отсортировала бы только текущую
страницу из 20 строк при 314 вопросах — это ложь, а не сортировка. Поэтому в UI
заголовки колонок сейчас не кликабельны.

**Просьба.** Общий контракт на все списки:

```
?sort=<field>&order=asc|desc
```

Минимальный набор полей по сущностям:

| Эндпоинт | Поля сортировки |
|---|---|
| `/admin/users` | `created_at`, `email`, `age_group`, `latest_assessment_status` |
| `/admin/universities` | `name`, `ranking`, `uniranks_kz_rank`, `programs_count`, `updated_at` |
| `/admin/feedback` | `created_at`, `relevance_score` |
| `/admin/questions` | `order`, `instrument`, `age_tier` |
| `/admin/directions` | `name`, `holland_code` |

Фронт готов: `AdminDataTable` принимает `sort` / `onSortChange` и рисует
индикатор направления, как только параметр появится.

## 2. Поиск там, где его нет

**Сейчас.** `search` есть только у `/admin/users` (по email),
`/admin/universities` (по `name`), `/admin/questions` (по тексту),
`/admin/directions` (по названию).

**Нет вообще.** `/admin/question-pairs`, `/admin/motivation-statements`,
`/admin/motivation-pairs`, `/admin/feedback`.

**Просьба.**

- `/admin/question-pairs?search=` — по `option_a_text` / `option_b_text` и по
  тексту связанных вопросов (fallback-значения).
- `/admin/motivation-statements?search=` — по `text` / `text_junior`.
- `/admin/motivation-pairs?search=` — по `text_a` / `text_b`.
- `/admin/feedback?search=` — по `comment`.
- `/admin/universities?search=` — расширить на `aliases`, `short_name`, `city`.
  Сейчас поиск матчит **только** `University.name`, из-за чего вуз не найти по
  городу или по общеизвестной аббревиатуре. Пока не сделано — на экране стоит
  честная подпись «только по названию».

## 3. Фильтры

| Эндпоинт | Просьба | Зачем |
|---|---|---|
| `/admin/feedback` | `?score_min=`, `?score_max=`, `?age_group=`, `?section=` | найти все негативные отзывы — сейчас невозможно |
| `/admin/motivation-statements` | `?triplet_index=`, `?category=` | триплет — смысловая единица, см. §7 |
| `/admin/motivation-pairs` | `?category=` | |
| `/admin/universities` | `?country=`, `?has_ranking=` | |
| `/admin/questions` | `?has_overrides=` | «покажи всё, что правили руками» |

Последнее (`has_overrides`) полезно для всех 5 контент-сущностей: это ровно тот
срез, который админ хочет проверить перед деплоем.

### `/admin/feedback` — подробнее

Это единственный экран, который целиком существует ради одного вопроса: «покажи
всё, что оценили на 1–2, и дай прочитать комментарии». Эндпоинт принимает только
`page` и `limit` — ни фильтра, ни поиска, ни сортировки. До редизайна на странице
прямо в интерфейсе стояла серая строка «фильтры по оценке ждут поддержки в API»:
честно, но пользоваться экраном это не помогало.

Просьба, по убыванию пользы:

| Параметр | Зачем |
|---|---|
| `?score_min=`, `?score_max=` | негативные отзывы — основной рабочий срез |
| `?has_comment=true` | комментарий есть примерно у половины; остальные строки читать нечего |
| `?age_group=`, `?section=` | сверить, где отчёт заходит хуже |
| `?search=` по `comment` | найти «не понял, откуда выводы» |
| `?sort=created_at\|relevance_score&order=` | |

**Временное решение на фронте.** `useFeedbackFeed` тянет весь список постранично
по `limit=100` (сегодня 63 отзыва — один запрос) и дальше фильтрует, сортирует и
пагинирует у себя. Обоснование ровно то же, что и для каталога вузов (§12), плюс
одно специфичное: `GET /admin/feedback/stats` **уже** выбирает все строки таблицы
и обогащает их в Python на каждый вызов — бэкенд сам считает эту таблицу
достаточно маленькой, чтобы пройти её целиком.

Два следствия:

- фронт больше **не вызывает `/admin/feedback/stats`**: сводка считается из тех же
  строк, что показывает таблица, той же группировкой, что и `_breakdown`
  (ключ → count → среднее). Так два числа на экране физически не могут
  разойтись, и сводка умеет следовать за фильтром — чего эндпоинт не умеет;
- ограничение `MAX_ITEMS = 1000` (10 запросов). Отзывы, в отличие от каталога
  вузов, растут вместе с пользователями, поэтому предел жёсткий. Строки приходят
  `created_at DESC`, так что усечённая выдача — это «последняя тысяча отзывов», у
  среза есть имя; страница пишет об этом плашкой.

**Как только появятся фильтры и `?sort=` — `useFeedbackFeed` удалить, вернуться к
серверной пагинации, а сводку взять из `/admin/feedback/stats`.** Заодно тогда
стоит добавить в `/stats` разбивку по самим оценкам (`score_counts`): гистограмма
1–5 — главный график экрана, а в ответе сейчас есть только среднее.

## 4. Снятие override / lock

**Сейчас.** Правка поля через PATCH создаёт override (контент) или запись в
`admin_locked_fields` (вузы/программы), который навсегда защищает поле от
сид-ресинка. **Обратного эндпоинта нет.** Ошибочная правка одной буквы
навсегда выводит поле из-под автообновления, и откатить это можно только
руками в БД.

**Просьба.**

```
DELETE /admin/questions/{id}/overrides/{field}      → снять один override
DELETE /admin/questions/{id}/overrides              → снять все, вернуть строку под банк
```

и то же для `question-pairs`, `motivation-statements`, `motivation-pairs`,
`directions`, а для `universities` / `programs` — снятие `admin_locked_fields`.

Хорошо бы в ответе detail отдавать и **исходное значение из банка** рядом с
override — тогда UI сможет показать «было / стало» и «вернуть как в банке»:

```jsonc
"overrides": {
  "text": { "value": "новый текст", "bank_value": "текст из банка" }
}
```

Фронт спроектирован под это: в форме уже есть место под «вернуть исходное»
рядом с каждым залоченным полем — кнопка появится, когда появится эндпоинт.

## 5. Активность пользователя

**Сейчас.** В `AdminUserListItem` есть только `created_at`. Колонка в UI до
редизайна называлась «АКТИВНОСТЬ» и показывала «2 дн назад» — это была дата
регистрации, читалось как «заходил 2 дня назад». В редизайне колонка честно
переименована в «Регистрация».

**Просьба.** `last_active_at` (последний запрос / последний ответ на вопрос) в
`AdminUserListItem` и `AdminUserDetail`. Это разблокирует:

- реальную колонку «Активность»;
- фильтр «неактивные N дней»;
- агрегат из §6.

## 6. Агрегаты, которых нет

**Обрывы диагностики.** В макете была плашка «брошено на диагностике: N».
Посчитать её на фронте нельзя: нужен срез по всей таблице
(«in_progress + нет активности N дней»), а список отдаёт страницу из 20 и не
имеет поля активности. До редизайна в UI стояла строка
«БРОШЕНО НА ДИАГНОСТИКЕ: НЕТ ДАННЫХ» — убрана как визуальный мусор.

**Просьба.** `GET /admin/users/stats`:

```jsonc
{
  "total": 1234,
  "signups_last_7d": 56,
  "abandoned_diagnostics": 12,   // in_progress без активности > 7 дней
  "completed_diagnostics": 890
}
```

**Скорость прохождения.** В `DiagnosticSummaryBlock` время по блокам считается
на фронте из `responses[].created_at` (реально, но приблизительно — это разница
между первым и последним ответом, а не активное время). Строка
«СКОРОСТЬ ПРОХОЖДЕНИЯ: НЕТ ДАННЫХ» убрана. Если нужна честная метрика — её
должен считать бэкенд.

## 7. Триплеты мотивации — валидация

**Сейчас.** У `MotivationStatement` есть `triplet_index`, и три утверждения
одного триплета **должны** иметь три разные категории. Бэкенд это не проверяет,
а в UI до редизайна стояла подпись «БЭКЕНД ЭТО НЕ ПРОВЕРЯЕТ» — валидация
перекладывалась на глаз админа, который при этом не видел двух других строк
триплета (фильтра `triplet_index` нет).

**Просьба, любая из двух:**

1. Серверная проверка уникальности категорий внутри триплета при PATCH (422 с
   понятным текстом), **или**
2. `GET /admin/motivation-statements?triplet_index=N`, чтобы фронт показал
   триплет целиком и проверил сам.

Второе дешевле и всё равно полезно для UI (см. §3).

## 8. Структура грантов программы

**Сейчас.** `AdminProgramDetail.grants` — нетипизированный массив, форма записи
нигде не описана. Из-за этого в админке гранты редактируются как **сырой JSON в
textarea**: одна опечатка — и `JSON.parse` падает, а при неудачной структуре
можно молча испортить данные.

**Просьба.** Задокументировать (или, лучше, типизировать в pydantic) форму
одной записи гранта — например:

```jsonc
{ "type": "state", "label": "Госгрант", "amount": 1200000, "count": 30, "note": "..." }
```

Как только форма зафиксирована, JSON-textarea заменяется на нормальный
структурный редактор. Пока — в UI стоит валидация JSON с блокировкой
сохранения и подсветкой ошибки, но это заплатка.

Тот же вопрос по `requirements` и `deadlines`: они сохраняются как
whole-object replace, и форма мёржит известные ключи поверх оригинала, чтобы не
потерять незнакомые (`admission_scores_2026` и т.п.). Список ключей, которые
там легально бывают, тоже стоит зафиксировать.

## 9. Настоящая роль вместо `is_admin`

**Сейчас.** `User`, `AdminUserListItem`, `AdminUserDetail` несут только
`is_admin: boolean`. Фронт выводил из него «Администратор / Оператор»
(`deriveAdminRole`), но живого оператора в системе не существует: `RequireAdmin`
пускает по `is_admin`, значит все — администраторы. `RoleGatedAction` и
тултип «Требует роли Администратор» ничего реально не гейтили.

**Решение на время PRO-242.** Различие ролей из UI убрано, чтобы интерфейс не
изображал разграничение прав, которого нет.

**Просьба, если роли нужны.** Настоящее поле `role: "administrator" | "operator"`
в `/auth/me` и админских схемах + серверная проверка на write-эндпоинтах.
Фронтовый гейт без серверного — это UI-театр, а не безопасность.

## 10. Действия над пользователем

**Сейчас.** Карточка пользователя показывает `is_admin` / `is_active` /
`is_verified` как «Да / Нет», но изменить ничего нельзя. Выдача админки — только
CLI-скриптом `scripts/make_admin.py`, удаление — `scripts/delete_user.py`.

**Просьба (если продукт этого хочет — вне скоупа PRO-242, но каркас место
предусматривает):**

```
PATCH  /admin/users/{id}    { "is_active": false }
PATCH  /admin/users/{id}    { "is_admin": true }
```

В редизайне на карточке зарезервирован блок действий: как только эндпоинты
появятся, кнопки встают туда без перекройки макета.

## 11. Экспорты CSV

### 11.1 Общее для всех CSV: нет UTF-8 BOM

Проверено побайтово на живых выгрузках — `users_export.csv` и все три файла
внутри ZIP начинаются сразу с заголовка, без `EF BB BF`:

```
$ xxd users_export-2.csv | head -1
00000000: 6964 2c65 6d61 696c ...   id,email...
```

Excel не определяет UTF-8 в `.csv` по содержимому: без BOM он читает файл в
кодировке системы, и вся кириллица превращается в кашу — «Бекзат» становится
«Ð‘ÐµÐºÐ·Ð°Ñ‚». А кириллицы в выгрузке много: имена профилей, а после
локализации (см. ниже) ещё и цель со статусом.

**Фронт закрыл это только для `users_export.csv`** — `downloadCsv()`
приписывает BOM перед сохранением. Файлы внутри ZIP так не поправить, не
распаковывая и не пересобирая архив в браузере, поэтому **`summary.csv`,
`responses.csv` и `motivation.csv` до сих пор ломаются в Excel**.

Просьба: писать BOM при сборке ZIP (`admin_export_service.assessment_detail_to_zip`).
Для `users_to_csv` — на усмотрение: BOM мешает `csv.reader`/pandas, а фронт
его уже добавляет сам, так что эндпоинт может остаться «чистым».

### 11.2 `users_export.csv`

Структура правильная: одна ровная таблица, стабильный порядок колонок,
экранирование через `csv` — тут всё хорошо. Что мешает:

- **`True` / `False`** в `is_verified`, `is_active`, `is_admin`, `has_profile` —
  питоновский литерал в файле, который открывают в Excel. Excel не считает их
  булевыми. Ожидается `да/нет` или `1/0`.
- **`created_at` в ISO с микросекундами и смещением** —
  `2026-09-03T09:29:27.080528+00:00`. Excel не распознаёт это как дату,
  сортировка и фильтр по дате не работают. Достаточно `2026-09-03 09:29`.
- **Машинные значения enum**: `age_group=senior`, `latest_assessment_goal=university`,
  `latest_assessment_status=completed`. В интерфейсе это «Senior»,
  «Поступить в вуз», «Завершён» — в выгрузке остались сырые ключи.
- **У junior все 11 колонок баллов пусты — и это не видно.** `riasec` намеренно
  не заполняется для junior (у него инструмент MI, а не RIASEC — так и написано
  в `_build_user_list_items`), но MI-колонок в CSV нет вообще. В файле такая
  строка выглядит как «диагностика завершена, баллов нет», то есть неотличима
  от битой. Просьба: либо колонки `mi_*`, либо колонка `instrument`, по которой
  видно, почему пусто.
- **Нет города и класса.** Для продукта по Казахстану региональный срез —
  очевидный вопрос к выгрузке, а `Profile.city` / `grade` в CSV не попадают.
- Нет `last_active_at` — см. §5.

### 11.3 Экспорт прохождения (ZIP)

Проверено на живой выгрузке: три CSV (`summary.csv`, `responses.csv`,
`motivation.csv`), данные полные и честные. Замечания:

- **Все 314 строк `responses.csv` несут два одинаковых `created_at`** — ответы
  пишутся пачкой в момент сабмита. Из-за этого любое «время на блок»,
  посчитанное по этим таймстемпам, всегда даёт ~0. Фронт такой расчёт убрал
  (раньше в сводке светилось «RIASEC: <1 мин», «Big Five: —»). Если время
  прохождения нужно как метрика — его должен писать бэкенд по ходу теста.
- **Колонка `category` в `responses.csv` смешивает две разные шкалы.** У RIASEC
  это буквы R/I/A/S/E/C, у Big Five — N/E/O/A/C. Буквы `A`, `E`, `C` есть в
  обеих, и в сводной таблице по одной только `category` «Артистичный» склеится
  с «Доброжелательностью». Разводит их соседняя колонка `instrument`, но об
  этом надо догадаться. Просьба: либо префикс (`riasec_A` / `big_five_A`), либо
  человеческое название шкалы рядом.
- **Заголовки колонок на английском** (`question_order`, `Metric,Value`), тогда
  как весь остальной интерфейс и содержимое CSV — на русском. Файл открывают
  в Excel не разработчики.
- **`has_roadmap,False`** — питоновский булев литерал в CSV. Ожидается
  `true/false` или `да/нет`.
- **Имя файла внутри `Content-Disposition`** — `assessment_<uuid>.zip`. Фронт
  теперь переименовывает скачиваемый файл в `profy_<имя>_<дата>.zip`, но
  заголовок с бэкенда стоит поправить тоже — иначе прямая ссылка отдаёт UUID.

## 12. Каталог вузов

- **`ranking` смешивает шкалы.** Модель прямо это оговаривает: в одном Integer
  лежат и позиция в мировом QS, и национальный тир, и отраслевой ранг. В списке
  это выглядит как сравнимые числа (32 и 248 рядом), хотя они несравнимы.
  Верное значение — в `ranking_label` («#28 (QS World)», «Top-20 (Нац.
  рейтинг)»), но его **нет в `AdminUniversityListItem`**. Просьба: добавить
  `ranking_label` в список, тогда колонка сможет показывать источник, а не
  голое число. Пока в UI стоит предупреждение в тултипе заголовка.

- **`updated_at` пуст у всех 252 вузов.** Он проставляется только при PATCH из
  админки, то есть до первой ручной правки колонка — это 252 прочерка. Фронт
  теперь показывает дату только у реально отредактированных строк. Отдельно
  полезно `updated_by` — сейчас непонятно, кто правил.

- **Сортировка по умолчанию ставит латиницу впереди кириллицы.** Казахстанские
  вузы (111 из 252) начинались с шестой страницы, хотя это основной рабочий
  срез.

- **5 вузов без программ.** Такой вуз никогда не попадёт в подбор ученику.

### Временное решение на фронте — и почему его надо будет снять

Три предыдущих пункта (страна, сортировка, поиск по городу) фронт закрыл
**загрузкой всего каталога целиком**: `useUniversityCatalog` вытягивает все
страницы по `limit=100` (сегодня это 3 запроса, ~70 КБ, ~0.25 с суммарно) и
дальше фильтрует, сортирует и разбивает на страницы у себя.

Это осознанный костыль, а не архитектура:

- он даёт то, чего эндпоинт не умеет: фильтр по стране, сортировку по любой
  колонке, поиск, который матчит ещё и город;
- альтернатива — фильтровать серверную страницу из 20 строк — была бы враньём:
  UI показывал бы «фильтрую каталог», фильтруя одну пятнадцатую;
- он ограничен `MAX_ITEMS = 2000`; при превышении страница честно пишет, что
  охватила не весь каталог.

**Как только появятся `?country=`, `?sort=&order=` и поиск по городу — хук надо
удалить и вернуться к серверной пагинации.**

## 13. Мелочи
- **`/admin/question-pairs` — в списке нет ни слова текста.** `AdminQuestionPairListItem`
  это `id`, `instrument`, `age_tier`, `pair_index`, `has_overrides` — и всё.
  До редизайна строка выглядела как «Пара #12 · RIASEC · Junior», ровно как
  соседние 66: найти нужную пару можно было только пересчётом. **Просьба:
  `option_a_text`, `option_b_text`, `frame` в элементе списка** (и `?search=`
  по ним, см. §2).

  *Временное решение на фронте:* `useDetailPreviews` дотягивает detail по
  каждой строке **видимой страницы** (максимум 20 запросов, по 6 параллельно,
  с кэшем на сессию) и показывает «Чинить самокат ↔ Играть в салки». Это N+1,
  и терпим он только потому, что банк — 67 строк и экран админский. Строка
  кликабельна и до подгрузки. **Удалить, как только текст появится в списке.**
- **`/admin/motivation-pairs` — та же беда.** `AdminMotivationPairListItem` это
  `id`, `pair_index`, `category_a`, `category_b`, `has_overrides`. Категорий
  девять, пар восемнадцать — то есть каждая подпись встречается ровно дважды и
  строку не различает. Просьба: `text_a` (и `text_b`) в элементе списка. Тот же
  `useDetailPreviews` закрывает это временно, 18 запросов на страницу.
- **`/admin/question-pairs`** — detail отдаёт `question_a_id` / `question_b_id`,
  но не резолвит fallback-текст связанного вопроса. Из-за этого фронт делает
  доп. запрос за каждым вопросом, чтобы показать, что реально увидит ученик.
  Просьба: вернуть в detail `question_a: { text, short_text, icon }` (и `b`).
- **`/admin/directions`** — нет связи с программами, хотя таблица
  `program_directions` существует. Просьба: `programs_count` в списке и список
  привязанных программ в detail.
- **`Direction.professions` пуст у всех 92 направлений.** Замерено, не оценка:

  ```sql
  select count(*) total,
         count(*) filter (where jsonb_array_length(professions) = 0) no_prof
  from directions;   -- 92 | 92
  ```

  Остальные поля каталога (`description`, `skills_needed`,
  `subjects_to_develop`, `first_steps`) заполнены у всех. То есть это не
  «каталог заполнен наполовину», а одно конкретное поле, пустое везде.

  Поле не декоративное — оно уходит в три места: `report_service.py` (отчёт
  ученика), `prompts/direction_inquiry.py` и `prompts/direction_roadmap.py`
  (контекст для LLM). Сейчас все три получают пустой список.

  Просьба к контенту, не к API: заполнить `professions` в сид-скрипте
  направлений. Пока не заполнено — карточка направления в админке прямо
  говорит, чего лишается продукт, вместо молчаливого пустого поля.
- **`AdminDirectionListItem`** не отдаёт полей каталога, поэтому в списке
  нельзя пометить направления с пустыми разделами. Просьба: флаг
  `catalog_filled` или счётчики — тогда появится фильтр «показать незаполненные».
- **`AdminUserDetail.profile`** — поля `subjects_liked` / `disliked` / `easy` /
  `hard` не объявлены в типе, фронт достаёт их через
  `record[`subjects_${kind}`]`. Просьба: объявить их в схеме явно.

## Что фронт сделал без бэкенда

Чтобы список выше не выглядел как «всё заблокировано» — вот что закрыто в
рамках PRO-242 только фронтом:

- единый фильтр-бар с состоянием в URL (ссылку на отфильтрованный список можно
  переслать коллеге);
- единая пагинация с переходом на страницу по номеру;
- единая таблица с адаптивом (карточки вместо строк на узком экране);
- единые состояния загрузки / пустоты / ошибки;
- панель сохранения: «черновик → сохранить», сброс, предупреждение при уходе
  с несохранёнными правками, явное объяснение, что именно залочится;
- хлебные крошки на всех detail-экранах;
- превью fallback-значений в парах вопросов (подгружается сразу, а не по
  кнопке);
- валидация Holland-кода и JSON грантов на клиенте;
- разбивка карточки тестирования на секции вместо одной простыни;
- фидбэк: гистограмма оценок 1–5 вместо одного среднего, все 5 разделов отчёта
  вместо топ-4, срезы по сценарию и направлению (бэкенд их считал, экран не
  показывал), клик по столбику = фильтр.
