# Profy Frontend — инструкции для Claude Code

## Локализация (обязательно, всегда)

В проекте включена локализация `ru` + `kk` (`i18next` + `react-i18next`).
Полный контракт — `docs/i18n.md`. Перед любой правкой UI-текста прочитать его,
если не читал в этой сессии.

Правила, которые нужно соблюдать **в каждой задаче**, где добавляется или
меняется текст, видимый пользователю (компоненты, страницы, тексты ошибок,
лейблы, тултипы, alt-тексты, плейсхолдеры, письма/уведомления и т.п.):

- **Никакого текста в JSX напрямую.** Только `t('namespace:key')` или
  `<Trans i18nKey="ns:key">` для строк с разметкой/ссылками.
- Новый ключ добавляется **сразу в оба каталога**:
  `src/shared/i18n/locales/ru/<namespace>.json` (источник правды) и
  `src/shared/i18n/locales/kk/<namespace>.json` (перевод или временная
  рабочая копия — не оставлять кириллицу `kk`-файла без перевода в PR).
- Числа с согласуемым существительным — через плюральные суффиксы
  i18next (`key_one/_few/_many/_other`), никаких ручных `mod10/mod100`
  хелперов и тернарников `n === 1 ? ... : ...`.
- Даты/числа/валюты — только через `src/shared/i18n/format.ts`
  (`formatDate`, `formatNumber`), не `toLocaleString()` с хардкодом локали.
- Справочники-константы (`*_LABELS`/`*_DESCRIPTIONS`/`*_HINTS` и т.п. в
  `src/shared/config/constants.ts`, `navItems.ts` и подобных) хранят
  **i18n-ключи**, а не текст.
- Админка (`/admin/*`) локализуется наравне с пользовательской частью —
  это не `ru`-only зона (см. «Исключения» в `docs/i18n.md`).
- Кириллица, которой фронт **парсит/сопоставляет** данные с бэка (а не
  показывает как UI-текст), — не локализуется, но помечается комментарием
  `// backend data / not UI copy` и вносится в `ALLOW` в
  `scripts/i18n-sweep.mjs` с причиной.

Перед тем как считать задачу с новым/изменённым текстом законченной, по
возможности прогнать:

```
npm run i18n:check   # parity + plurals + sweep разом
```

Если правишь только код без доступа к `npm` в моменте — минимум проверить
вручную, что каждый новый `ru`-ключ имеет пару в `kk` и ключ не остался
захардкоженной строкой в JSX.

## Переиспользование компонентов (обязательно, всегда)

Перед тем как писать новый компонент/разметку — сначала проверить, нет ли
уже подходящего:

- Общая библиотека — `src/shared/ui/` (баррель-экспорт `src/shared/ui/index.ts`:
  `Button`, `Input`, `Card`, `Badge`, `ProgressBar`, `Spinner`, `Skeleton`,
  `Tooltip`, `PageContainer`, `PageHeader`, `SectionHeading` и т.д.) и её
  подпапки `icons/`, `navigation/`, `layouts/`, `typography/`, `admin/`,
  `mascot/`. Новый общий элемент интерфейса — сюда, с экспортом через
  `index.ts`, а не копипастой разметки в очередной странице.
- Специфичные для экрана компоненты живут в `src/pages/<page>/components/`.
  Если компонент понадобился на второй странице — не копировать файл, а
  поднять его в `src/shared/ui/` (или в `shared/lib`/`shared/hooks`, если
  это логика, а не разметка) и импортировать оттуда в обоих местах.
- Прежде чем добавлять новую зависимость-компонент (UI-кит, иконки,
  модалка и т.п.) — проверить, нет ли уже эквивалента в `shared/ui` или в
  используемых библиотеках (`grep`/поиск по названию функции перед `npm i`).
- Не плодить варианты одного и того же компонента через `if`/copy-paste —
  расширять существующий пропсами (`variant`, `size` и т.п.), как это
  сделано в `Button`/`Badge`/`ProgressBar`.

## Тёмная тема (обязательно, всегда)

Тема — три состояния (`system`/`light`/`dark`), логика в
`src/shared/lib/theme.ts` и `src/shared/hooks/useTheme.ts`, применяется как
класс `.dark` на `<html>` (`@variant dark` в `src/styles/tailwind.css`).
Все цвета — CSS-переменные (design tokens) в `src/styles/theme.css`,
которые **переопределяются целиком** под `.dark { ... }`, поэтому обычный
компонент ничего не знает про тему и получает тёмный вариант бесплатно.

- **Никаких хардкод-хексов/`rgb()` в компонентах** (`style={{ color: '#...' }}`,
  `className="text-[#26332F]"`). Только семантические токены:
  `var(--pine)`, `var(--text-heading)`, `var(--bg-page)`, `var(--border)` и
  т.д. через `style={{ color: 'var(--token)' }}` или Tailwind arbitrary value
  `text-[color:var(--token)]` / `bg-[color:var(--token)]`.
- **Не использовать Tailwind-вариант `dark:`** (`dark:bg-...`,
  `dark:text-...`) — в проекте этот паттерн не применяется; тема
  переключается на уровне токена в `theme.css`, а не в разметке компонента.
  Если нужного оттенка под тёмную тему ещё нет — завести/поправить токен в
  `theme.css` (в обоих блоках, `:root`/`.theme-day` и `.dark`), а не
  городить условный класс в компоненте.
- Если токена под нужный цвет ещё нет — сначала посмотреть, нет ли
  подходящего в существующей палитре (`--midnight/--ink/--mute/--fog/--paper/
  --line/--hairline/--pine/--dawn/--lake/--clay` + `-light`/`-deep` варианты
  и семантические алиасы вроде `--bg-page`/`--text-heading`), и только потом
  заводить новый — с парой значений для светлой и тёмной темы.
- Поверхности, которые всегда светлые несмотря на тему (например, лист
  печати/экспорт в PDF), — через класс `.theme-day`, не через отключение
  токенов вручную.
- Перед сдачей задачи, где менялась разметка/стили, — переключить тему
  (`ThemeToggle` в UI или класс `dark` на `<html>` в devtools) и проверить
  экран в обоих режимах, не только в том, в котором вёлся разработка.

## Типографика (обязательно, всегда)

Три роли, выбор по авторству текста, не по «на глаз» размеру. Подробности —
`.cursor/rules/typography.mdc`.

- Заголовки/акценты — `<Heading level="display-lg|md|sm">` (`type.display*`),
  максимум 1–2 на экран, никогда не для кнопок/повторяющихся карточек.
- Обычный текст (вопросы, описания, лейблы) — `<Text variant="body-lg|md|sm|caption">`
  (`type.body*`/`type.caption`) — дефолт для всего написанного человеком.
- Машинный/системный текст (id, даты, статусы, коды, шапки колонок в
  админке) — `<Mono variant="label|sm|md">` (`type.mono*`).
- **Запрещено** `text-[14px]`, инлайновый `font-size`/`line-height`/
  `letter-spacing`. Если нужного размера нет — завести именованный токен в
  `src/styles/tailwind.css` (`@theme`), а не писать произвольное значение.
  Уже enforced ESLint-правилом `local/no-arbitrary-text-size`
  (`npm run lint`) и `npm run lint:typography` — но лучше не писать так с
  самого начала, чем чинить по красному линту.
- Один размерный ряд для всех возрастов (6–18 лет) — разница в подаче через
  текст/копирайтинг, а не через размер/жирность шрифта.

## Работа с данными (API, обязательно, всегда)

- Весь HTTP — только через `src/shared/api/client.ts` (`apiClient`). Не
  создавать второй `axios.create()`/использовать голый `fetch` в фиче —
  интерцепторы `apiClient` кладут `Authorization` и `Accept-Language`
  (см. `docs/i18n.md`), в обход них запрос уйдёт без токена и без локали.
- Серверные данные — через `@tanstack/react-query` (`useQuery`/`useMutation`)
  поверх `apiClient`, не через `useEffect` + ручной `useState`.
- `zustand` (`src/shared/store/`) — только для клиентского состояния
  (текущий пользователь/сессия, выбранная локаль, прогресс прохождения
  диагностики и т.п.), при необходимости персистентного — через
  `persist()` middleware (см. `auth.ts`, `locale.ts`, `assessment.ts`), а
  не как замена кешу серверных данных.

## Роутинг и доступ (обязательно, всегда)

Все маршруты объявлены централизованно в `src/app/router.tsx`, ничего не
регистрируется по месту. Комментарии `// mobile: ...` в нём — не мусор, а
карта соответствия мобильному приложению; при добавлении/переносе роута
стоит держать эту карту в уме.

- Новый защищённый экран — оборачивать существующим guard'ом из
  `src/shared/guards/` (`RequireAuth`, `RequireAdmin`, `RequirePsychologist`,
  `RequireStudent`, `RequireGuest`, `RequireProfile`), а не проверять
  токен/роль вручную в компоненте. Порядок вложенности guard'ов в дереве
  соответствует реальным ограничениям (роль → наличие профиля), не
  порядку добавления — новый роут вкладывается в подходящий уровень, а не
  всегда в самый внешний.
- Экран без чужого «хрома» (полноэкранный визард, печатная/PDF-версия) —
  выносится из-под `AppLayout`/`AdminLayout` в дереве роутов, а не
  получает проп типа `hideChrome`.
- **Ровно один** catch-all `path: '*'` на всё приложение, снаружи всех
  guard'ов, в самом конце. Раньше их было два (второй — внутри `AppLayout`
  под `RequireAuth`/`RequireProfile`), и вложенный побеждал: несуществующий
  адрес превращался не в 404, а в тихий редирект на `/login` или онбординг.
  Не заводить второй `*` внутри защищённого поддерева.

## Импорты (обязательно, всегда)

Алиас `@/...` (= `src/`, настроено в `tsconfig.json`) вместо цепочек
`../../../`. Относительные импорты — только для файлов в одной папке/по
соседству.

## Мёртвый код

При удалении/переносе фичи — прогнать `npm run knip` и убрать то, что он
пометил как неиспользуемое (экспорты, файлы), а не оставлять их «на
всякий случай».

## Доступность (a11y, обязательно, всегда)

Продукт — для 6–18 лет, часть экранов на drag-and-drop (`@dnd-kit`,
напр. `TripletRanking`). Для новых dnd-виджетов — не пропускать
`accessibility={{ announcements, screenReaderInstructions }}` (см.
`src/pages/assessment/components/TripletRanking.tsx`): без него
клавиатурный/скринридер-сценарий молча ломается, хотя мышью всё работает.
Тексты объявлений — такие же i18n-ключи, как остальной UI-текст, не
хардкод.

## Тесты

В проекте сейчас нет тестовой инфраструктуры (0 `*.test.*`/`*.spec.*`
файлов, нет `vitest`/`jest` в зависимостях). Не заводить её по своей
инициативе (конфиг, первый тестовый файл, тестовый раннер в `package.json`)
без явной просьбы — это отдельное архитектурное решение, а не часть
обычной задачи.
